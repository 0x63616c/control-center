# Codebase Audit — world-wide-webb @ a1466ac25 — 2026-08-01

## Health summary

The live single-node Talos cluster is healthy and the source is stronger than most home Kubernetes setups: Talos configuration is declarative and validated, first-party images are digest-pinned, local storage has enforced LVM capacity, service-account tokens are disabled by default, data backups leave the node, and metrics/logs/dashboards are managed as code. The concentrated risks are not the intentionally accepted single-node topology; they are avoidable gaps around it: a retired production stack is still executable, autonomous code execution has unrestricted networking, backups are not atomically published or continuously restored, etcd has no off-node snapshot path, dashboards do not alert, and the shared workload abstraction cannot encode the health and security defaults needed at 10x scale.

## Deployment safety

### H1 — Tombstone the retired Pulumi `prod` stack  `🔴 high · S · CONFIRMED`

**Current:** [`infra/Pulumi.prod.yaml`](../infra/Pulumi.prod.yaml) still selects `cc-homelab` and declares two cloudflared replicas at lines 2-3. [`infra/program.ts`](../infra/program.ts) accepts that stack: lines 141-159 default a missing substrate to OrbStack and pass the two-replica tunnel configuration into deployment. CI is correctly pinned to `STACK=home-server` at `.github/workflows/ci.yml:977-983`, but a local `pulumi up --stack prod` remains capable of waking the retired mini stack and split-braining the live Cloudflare tunnel.

**Proposed:** Fail closed in the Pulumi program, then archive/delete the Pulumi backend stack after preserving its state history.

```diff
 const stackName = pulumi.getStack();
+if (stackName === "prod") {
+  throw new Error(
+    'Pulumi stack "prod" targets the retired Mac mini and is permanently disabled; use "home-server".',
+  );
+}
```

**Why:** “Never deploy this” is documentation, not a control. The failure mode is externally visible traffic split across two clusters and is easy to trigger with an old command copied from the repo’s stale docs.

**Verification:** Run a no-credential unit test that sets the stack to `prod` and expects the tombstone error; confirm `pulumi preview --stack home-server` still renders normally; search for operational `--stack prod` instructions before archiving the backend stack.

## Security boundaries

### H2 — Isolate autonomous Run Worker networking  `🔴 high · M · CONFIRMED`

**Current:** The current V0 factory routes tools to plain Run Worker Pods (`apps/software-factory/internal/agent/runtime.go:27-53`, `apps/software-factory/internal/clients/k8s/runworker_podspec.go:114-165`). Those pods are well hardened locally: no service-account token, non-root UID, dropped capabilities, RuntimeDefault seccomp, deadlines, and split credential/tool responsibilities. They do not set a `runtimeClassName`, however, and the live cluster uses Flannel 0.28.7 with zero NetworkPolicies. A model-driven Run Worker therefore has normal pod egress to cluster Services and routable LAN destinations. The webhook HMAC at `apps/software-factory/internal/webhook/webhook.go:67-73` protects one internal endpoint, not the network boundary.

**Proposed:** Choose and install a policy-enforcing data plane, then make `software-factory` default-deny for ingress and egress. Add narrow role-specific policy for DNS and the exact Temporal, blob, codec, API, GitHub, and OpenAI paths required. Separately decide whether Run Workers should return to the already-installed Kata runtime; network policy and VM isolation solve different problems.

**Why:** This is autonomous execution over attacker-influenceable repository and ticket content on the same network as home automation, databases, internal APIs, and the LAN. Container hardening limits privilege escalation but does not limit reachable targets or exfiltration.

**Verification:** Before changing CNI, inventory every required destination from a real successful Run. After rollout, prove default-deny with an unauthorized cluster Service and LAN address, then prove the full factory acceptance path still succeeds. Confirm policies are enforced, not merely accepted by the API server.

## Backup and disaster recovery

### H3 — Publish Postgres backups atomically  `🔴 high · S · CONFIRMED`

**Current:** `postgresBackupCommand()` writes `pg_dump | gzip` directly to the final date-only `.sql.gz` at `infra/src/crons.ts:55-72`; the Home Assistant backup repeats it at lines 182-191. Shell redirection truncates an existing same-day file before the dump begins, so an interrupted retry can replace a good backup with a partial artifact. `set -eo pipefail` correctly makes the Job fail, but it does not remove the partial final file. The blob backup already uses the right local precedent at lines 132-138: write a temporary file, then rename.

**Proposed:** Reuse one atomic archive helper for every database backup.

```diff
 out="${backupMountPath}/${backup.filenamePrefix}$(date +${backup.dateFormat}).sql.gz"
-pg_dump -h ${backup.serviceHost} -U ${backup.owner} -d ${backup.databaseName} | gzip -c > "$out"
+tmp="$out.tmp"
+trap 'rm -f "$tmp"' EXIT
+pg_dump -h ${backup.serviceHost} -U ${backup.owner} -d ${backup.databaseName} | gzip -c > "$tmp"
+gzip -t "$tmp"
+mv "$tmp" "$out"
+trap - EXIT
 echo "wrote $out"
```

Apply the identical helper to Home Assistant rather than keeping a second shell implementation.

**Why:** Backup presence is not backup validity. A failed rerun must leave the last known-good artifact untouched and must not create a final-looking corrupt file.

**Verification:** Unit-test rendered commands for temp path, `gzip -t`, rename, and cleanup. Execute a scratch backup, kill it mid-stream, and confirm no final artifact changes; then complete one and restore it.

### H4 — Bound backup Job execution  `🔴 high · S · CONFIRMED`

**Current:** `CronJobSpec` documents and supports `activeDeadlineSeconds` at `infra/src/component.ts:145-149` and renders it at lines 620-649. None of the Postgres, Home Assistant, or blob backup declarations sets it (`infra/src/crons.ts:80-105,120-155,165-203`). Live, all four backup CronJobs combine `concurrencyPolicy: Forbid` with no active deadline. Their backup PVs are hard NFSv4 mounts, so one wedged Job can suppress later schedules indefinitely.

**Proposed:** Give every backup a deliberate wall-clock bound, initially two hours, and alert on deadline failure or missed completion.

```diff
 return {
   name: backup.name,
   schedule: backup.schedule,
+  activeDeadlineSeconds: 2 * 60 * 60,
   command: postgresBackupCommand(backup),
```

Add the same field to `homeAssistantPgBackupCronSpec()` and `softwareFactoryBlobsBackupCronSpec()`.

**Why:** `Forbid` is correct for non-overlapping backups only if every run has a terminal path. A hung mount otherwise silently turns one incident into permanent loss of future backups.

**Verification:** Render every CronJob and assert a nonzero deadline. In a scratch Job, simulate a long-running process and verify the Job becomes failed and a later schedule is admitted. Separately document that a kernel-level uninterruptible NFS mount can still require node/NAS recovery.

### H5 — Continuously prove database restores  `🔴 high · M · CONFIRMED`

**Current:** Nightly writers exist, and `scripts/pg-snapshot-restore.sh:24-27,123-156` provides a guarded scratch restore plus count comparison. `docs/k3s-migration/cc-restore-rehearsal-report.md:1-33` records a real historical rehearsal. Repository-wide search found no workflow or schedule that restores current nightly artifacts; only the helper’s hermetic test invokes it.

**Proposed:** Add a periodic recovery workflow that selects the newest artifact for every product database, restores it into an isolated scratch Postgres, runs `pg_restore --list`/restore, validates schema and product invariants or table counts, emits duration/freshness metrics, and destroys the scratch target. Keep destructive production restore manual.

**Why:** The existing rehearsal proves the process once. It does not detect a later server-version mismatch, permissions change, truncated/current artifact, missing table, or backup job that has quietly stopped producing useful output.

**Verification:** Prove the workflow fails on a corrupt gzip, a dump incompatible with the target toolchain, and an invariant mismatch. Record the last successful restore timestamp per database and alert when stale.

### H6 — Add off-node Talos etcd snapshots  `🔴 high · M · CONFIRMED`

**Current:** `infra/talos/talconfig.yaml:17-21` declares one control-plane node. The repository contains the encrypted Talos cluster secrets and a proven application rebuild path (`docs/runbooks/local-lvm-cutover.md:20-25,79-120`), but no `talosctl etcd snapshot` automation, off-node snapshot upload, etcd restore procedure, or etcd-specific rehearsal was found. Any external untracked snapshot system is unverified.

**Proposed:** Schedule an operator-side snapshot from a trusted runner or admin host, encrypt it, copy it to independent storage, bound retention, and add a periodic disposable restore/bootstrap rehearsal. Document which dynamic cluster state matters beyond Pulumi, especially operator state and runtime-created factory resources.

**Why:** Single-node downtime is accepted; unnecessary loss of all Kubernetes state is not. Application backups can rebuild data, but an etcd snapshot materially reduces recovery time and preserves state that is not declaratively recreated.

**Verification:** Inventory snapshot contents and encrypted destination without exposing secrets. Rebuild a disposable control plane from a snapshot using the committed Talos secrets, verify API objects, then record measured RPO/RTO and rotation behavior.

## Operability

### H7 — Turn observability into alerting  `🔴 high · M · CONFIRMED`

**Current:** The metrics, logs, recording rules, and dashboards are substantial, but alert delivery is explicitly excluded: `docs/adr/0007-hand-rolled-observability-stack.md:82-84` and `docs/observability.md:396-401` state there is no Alertmanager, alert rules, or Loki ruler. `infra/src/observability/rules.ts:12-19` strips alerting rules. Failures are discovered only when someone looks or when CI itself fails.

**Proposed:** Add the smallest actionable alert pipeline to the existing notification channel. Start with node/API unavailable, CNPG unhealthy, backup missed/failed, restore proof stale, PVC/VG/EPHEMERAL pressure, certificate expiry, CrashLoop/OOM, Temporal backlog, and factory terminal failure. Every alert needs a runbook link, delay, and recovery notification; avoid porting a generic ruleset wholesale.

**Why:** Dashboards shorten diagnosis after discovery. They do not discover a 3am failure, and the most important backup/recovery guarantees currently have no freshness signal.

**Verification:** Unit-validate Prometheus rules, exercise each alert with synthetic series or a safe failure injection, verify delivery and resolution through ntfy, and confirm labels do not leak secret or high-cardinality data.

## Scale readiness

### H8 — Deepen the shared Workload primitive  `🔴 high · M · CONFIRMED`

**Current:** `WorkloadSpec` cannot express readiness, liveness, startup probes, pod security context, or container security context (`infra/src/component.ts:68-129`); its renderer also omits them (`infra/src/component.ts:180-207,529-580`). Live, all eight containers in the shared-renderer `control-center` and `home-assistant` workloads lack readiness probes, liveness probes, and container security contexts. The primitive does correctly disable service-account token mounting, set resources, and select `Recreate` for RWO claims. Hand-written factory workloads demonstrate the missing baseline at `infra/src/software-factory.ts:409-518,727-787`.

**Proposed:** Make `Workload` a real golden path: typed HTTP/TCP/exec probes, secure pod/container defaults, explicit exception reasons, termination grace, and rollout policy. Prefer small workload profiles such as `httpService`, `worker`, and `statefulSingleReplica` over exposing raw Kubernetes fields everywhere. Migrate one representative service, validate rendered/live behavior, then move the rest.

**Why:** At 10x workloads, copying special hand-written Deployments guarantees drift. A deeper primitive makes the safe path shorter, creates one enforcement point, and lets CI reject workloads that lack health semantics or carry unexplained privilege.

**Verification:** Add render tests for defaults and exceptions; ensure every Service-backed workload has a readiness probe; inject slow startup and unhealthy responses during a rolling deployment; validate images that cannot run non-root before enforcing the default cluster-wide.

## Supply-chain determinism

### M1 — Pin the Home Assistant image immutably  `🟡 med · S · CONFIRMED`

**Current:** `infra/src/homeassistant.ts:199-206` deploys `ghcr.io/home-assistant/home-assistant:stable`; the live Deployment uses the same mutable tag. The first-party digest guard does not cover this external image. The live image currently resolves to `sha256:5a531753cea96444200158fc2b0ac7ccd739291ec50414877b396de6e0bb29b3`.

**Proposed:** Pin the known live artifact now, then adopt an explicit upgrade-and-test cadence.

```diff
-image: "ghcr.io/home-assistant/home-assistant:stable",
+image: "ghcr.io/home-assistant/home-assistant@sha256:5a531753cea96444200158fc2b0ac7ccd739291ec50414877b396de6e0bb29b3",
```

**Why:** A pod reschedule can otherwise pull different software without a Git change or Pulumi diff. That breaks reproducibility, rollback, and incident correlation for a central home service.

**Verification:** Confirm the digest matches the intended Home Assistant release and architecture, run the existing HA tests, preview the Deployment change, and verify HA health plus integrations after rollout.
